## Database table descriptions

### `jds` table

Stores job descriptions, scores, and lead status. Key columns: `company`, `role`, `file_path`, `score`, `evaluated_at`, `source` ('primary'/'secondary'), `lead_status` ('pending'/'approved'/'declined'/'applied' — declined = seeker passed on the lead, vs. `applications.status='rejected'` = company rejected the seeker), `lead_decided_at` (when the lead left 'pending' for a triage decision — distinct from `evaluated_at`, when it was scored), `decline_reason` (the seeker's own one-line reason for passing, vs. `summary` = the evaluate-job fit analysis), `decline_category` (see below), `url` (canonical posting link), `salary_min`, `salary_max`.

#### Decline categories

`decline_reason` reads well and aggregates not at all. `decline_category` is its groupable counterpart — one slug per decline, defined once in `utils/triage_lead.py:DECLINE_CATEGORIES`, which the triage prompt, the `Decline Patterns` report, and the `Declined Leads` board all render from so the wording cannot drift:

| slug | meaning |
|---|---|
| `domain` | industry/sector outside the target |
| `stack` | hard-requirement tech the seeker doesn't have |
| `role_type` | wrong *kind* of job — support, management, platform vs. product QA |
| `level` | right job, wrong seniority (over- or under-leveled) |
| `comp` | salary below the seeker's floor |
| `location` | geo or onsite requirement |
| `strategy` | the posting was fine; the seeker is focusing elsewhere |
| `other` | none of the above; `decline_reason` carries it |

Two rules that keep the numbers meaningful. **One primary category per decline** — most declines are layered, so store the decisive one and let `decline_reason` carry the rest. And **`strategy` is not `other`**: a `strategy` decline is fully explained (nothing was wrong with the posting), while `other` means unclassified, so the report counts `strategy` outside "market signal" and `other` in neither column. There is no `CHECK` constraint; the vocabulary is validated in Python, matching how `lead_status` is handled.

Triage decisions go through `python3 -m best_foot_forward.utils.triage_lead --file-path <path>|--jd-id <id>|--company <name> [--role <role>] --status <pending|approved|declined|applied> [--category '<slug>'] [--reason '<why you passed>'] [--decided-at '<iso datetime>']`, which is the single write path for those four columns — it stamps `lead_decided_at`, keeps `decline_reason`/`decline_category` attached to a live decline (clearing them if the lead is later reconsidered), and clears all three when a lead is put back to `pending`. Declining on a TTY without `--category` prompts with the glossed menu; a non-interactive run leaves it NULL and the report counts it as uncategorized rather than blocking. `track_application.py` calls it for the `applied` transition.

**`--decided-at` matters when re-triaging.** A re-triage overwrites all four columns, so adding a category to an older decline without passing its existing `lead_decided_at` (and its existing `--reason`) restamps it as decided today and blanks the reason. Pass both.

Adding the columns to an existing DB: `python3 scripts/migrate_lead_decision.py`, then `python3 scripts/migrate_decline_category.py` (both idempotent; the first backfills `lead_decided_at` from `evaluated_at` for already-declined leads, the second adds a nullable column and backfills nothing — categories are a judgement call made per lead through `triage_lead`).

#### Saving a lead's JD text at evaluation time

`python3 -m best_foot_forward.utils.save_lead_jd --company '<Co>' --role '<full title>' [--url <url>] --text-file <path|->` writes `{Company}_{Role_Slug}JobDesc.md` into the asset tree and indexes what it says. Run it *before* the score UPDATE; it prints the `jd_id` to key that UPDATE on.

Why it exists: the JD file used to be written only during *tailoring*, and a lead you pass on is never tailored. So every declined lead had no JD text on disk and zero `jd_required_skills` rows — the declined reports could rank by score and salary but could never say what the jobs had in common technically. Evaluation is the one moment the text is guaranteed to be in hand.

It reuses the shared helpers rather than reimplementing them: `slugify()` for the path (never hand-derived), `db.resolve_or_create_jd()` for the row, and `jd_skills.extract_terms` for the indexing. It also registers the file in `file_registry`, which JD files never were.

#### `jd_required_skills` and the skill-gap vocabulary

`jd_required_skills` used to be populated from a vocabulary built entirely out of the user's own `skills` table (plus a small hardcoded list) — so it could only ever contain skills the user already had, and the gap report (`bff gaps`) was subtracting a profile from a set derived from that same profile. Fixed via `src/best_foot_forward/utils/jd_skills.py`: a shipped reference lexicon (`src/best_foot_forward/lexicon/tech_lexicon.json`) provides an open vocabulary independent of any profile, plus optional LLM-extracted labels from evaluate-job's scoring subagent (`save_lead_jd --skills-json`), unioned with the (still-present, now-secondary) skills-table scan. Two new columns: `canonical_label` (alias-normalized display form — "k8s" and "kubernetes" both become "Kubernetes", which is what lets equivalent mentions across JDs aggregate) and `source` (`lexicon` | `profile` | `llm`).

`reports/skills.py::view_gaps` groups on `COALESCE(canonical_label, lower(skill_label))` and prints a health-check banner if the indexed vocabulary looks suspiciously closed (>90% already-known terms) — that's the only signal distinguishing "no gaps" from "gaps got filtered out before the query ran."

Existing rows: `python3 scripts/migrate_jd_skill_canonical.py` adds the columns (idempotent, no value backfill — that's a judgment call, not a schema migration). Then `python3 -m best_foot_forward.utils.reindex_jd_skills --all` re-extracts from source text where a JD file is still readable, or re-canonicalizes existing labels in place for imported rows with none.

Three behaviours worth knowing:
- **It never writes `score`, `summary` or `evaluated_at`** — those belong to evaluate-job.
- **Salary and URL are filled, never replaced.** A range read off a posting's sidebar by hand survives a later parse that finds nothing in the body text.
- **A row it creates lands `lead_status='pending'`**, named explicitly on insert because the schema `DEFAULT` is still `'approved'`. A row it finds or adopts keeps whatever triage state it already had.

**It deliberately does not call `scan_jds.py`.** Without `--rescan`, `scan_jds` skips any file whose `file_path` already has a `jds` row — which the evaluate-job flow always creates — so it would do nothing at all. `--rescan` used to compound this by overwriting `evaluated_at` with the scan time, replacing when a lead was *scored* with when it was *scanned*; as of the `COALESCE` fix a scan fills that column only when it is NULL, so `evaluated_at` means "scored" everywhere. `save_lead_jd` still owns extraction at evaluation time — `scan_jds` is the fallback for JD files that were already in the asset tree and never went through it.

#### Reporting on declines

- `python3 src/best_foot_forward/cli.py declined` — the list: score, salary, decision date, category, reason, fit analysis, posting URL.
- `python3 src/best_foot_forward/cli.py patterns` — the roll-up: counts and average score/salary per category, the market-signal vs. pipeline-choice split, repeat companies, and declined-vs-applied counts by score band. Not to be confused with `passes` ("Pass/Decline Analysis"), which is the mirror image: companies that rejected *you*.

Both reports print a posting URL per lead, preferring `file_registry.source_urls` and falling back to `jds.url`. The fallback is what makes them useful at all for declines: a JD file is only written during tailoring, so a lead that was passed on has no `file_registry` row and the URL lives solely on `jds.url`.

### `stories`, `story_themes`, `story_bullets`

STAR corpus. Each story has structured STAR fields (situation/task/action/result), an `employer_id` link, a `raw_transcript` for voice analysis, and `source_type`/`source_file` for provenance. `story_themes` uses the same theme vocabulary as `bullet_themes`. `story_bullets` links each story to the bullets derived from it — every bullet should ideally trace back to a source story. `stories.readiness`: 'draft' | 'ready' | 'practiced'.

### `story_interview_use`

Tracks which stories were used in actual interviews. Columns: `story_id`, `application_id`, `question_prompt`, `used_at`, `outcome_notes`.

### `applications`

One row per tailored application. Links to `jds` via `jd_id`. Key columns: `status`, `stage`, `applied_at`, `concluded_at`.

#### Offer acceptance

Eight offer columns live directly on `applications` rather than a separate `offers` table — an offer belongs to exactly one application, and `jds` already carries its own salary columns inline (`salary_min`/`salary_max`/`salary_target`), so this follows the same pattern instead of introducing a join: `offer_received_at`, `offer_salary`, `offer_total_comp`, `offer_currency`, `offer_title`, `offer_start_date`, `offer_deadline`, `offer_notes`. What this shape can't hold is a renegotiation history on a single offer — that goes in `notes`, which is append-only by convention, same as `offer_notes`.

Three states move `stage`/`status`/`concluded_at` together: `received` → `offer_received`/`offer` (not concluded — still deciding), `accepted` → `offer_accepted`/`accepted` (concluded), `declined` → `declined_offer`/`offer_declined` (concluded). All three go through `python3 -m best_foot_forward.utils.record_offer --application-id <id>|--jd-id <id>|--company <name> [--role <role>] --state <received|accepted|declined> [--salary <n>] [--total-comp <n>] [--currency <ccy>] [--title '<t>'] [--start-date <iso>] [--deadline <iso>] [--received-at <iso>] [--decided-at <iso>] [--notes '<...>']`, the single write path for those columns — mirroring how `triage_lead` owns the lead-decision columns above. Terms are combined with `COALESCE` against the existing value on every call, so a later `--state accepted` after an earlier `--state received` adds the final numbers without blanking what was already captured.

The same module's `close_applications(conn, ids, status, reason)` (`--close-ids <id,id,...> --close-status withdrawn|not_pursued [--close-reason '<...>']`) is the withdraw/not-pursue sweep run alongside an acceptance — always explicit ids, guarded by `concluded_at IS NULL` so re-running it never stomps a row already closed for a different reason (a genuinely rejected application stays rejected).

Adding the columns to an existing DB: `python3 scripts/migrate_offer_columns.py` (idempotent; no backfill — there's no offer data anywhere to backfill from, it only ever lands through `record_offer`).

### `file_registry`

Every file BFF creates or discovers, linked back to the jd/application that produced it.

| Column           | Description                                                                                                                            |
| ---------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| `file_path`      | Relative path from project root (e.g. `data/BestFootForward/assets/Acme/Engineer/resume.docx`). UNIQUE.                                |
| `file_type`      | One of: `jd`, `resume`, `letter`, `screen_prep`, `interview_prep`, `transcript`, `recording`, `questions`, `notes`, `research`, `misc` |
| `summary`        | Short label (1–2 sentences) auto-generated from type + company/role                                                                    |
| `description`    | Optional fuller context; blank for auto-registered files unless manually added                                                         |
| `jd_id`          | FK to `jds` (SET NULL on delete)                                                                                                       |
| `application_id` | FK to `applications` (SET NULL on delete)                                                                                              |
| `story_id`       | FK to `stories` (SET NULL on delete) — used for transcripts and recordings                                                             |
| `file_size`      | Bytes on disk at registration time                                                                                                     |
| `file_mtime`     | ISO datetime of last disk modification at registration time                                                                            |
| `registered_at`  | When the registry entry was first created (never updated by upsert)                                                                    |
| `source`         | `auto` (generated by a BFF script), `sync` (discovered by sync_files.py), or `manual`                                                  |

**What registers files automatically:** `generate_resume.py`, `generate_letter.py`, `track_application.py`, and `transcribe.py` all call `db.register_file()` immediately after writing a file.

## File registry workflow

### Backfill / sync (existing installs)

```bash
python3 src/best_foot_forward/utils/sync_files.py --dry-run   # preview
python3 src/best_foot_forward/utils/sync_files.py             # register all new files
```

Safe to run repeatedly — already-registered files are skipped unless `--refresh` is passed.

### Useful flags

```bash
--dry-run         # print what would be registered without writing
--refresh         # re-stat already-registered files (updates file_size, file_mtime)
--company Acme    # limit scan to one company folder
--check-orphans   # report missing-on-disk registry entries + unregistered files on disk
```

### Orphan check

```bash
python3 src/best_foot_forward/utils/sync_files.py --check-orphans
```

Reports two lists: (a) registry entries whose file no longer exists on disk, (b) files on disk not yet in the registry. Run this after reorganizing the `data/applications/` directory.

### Querying the registry

```bash
# Files by type
sqlite3 data/best_foot_forward.db \
  "SELECT file_type, COUNT(*) FROM file_registry GROUP BY file_type;"

# All files for a company
sqlite3 data/best_foot_forward.db \
  "SELECT fr.summary, fr.file_path FROM file_registry fr
   JOIN jds j ON fr.jd_id = j.id WHERE j.company = 'Acme';"

# Files not linked to any JD
sqlite3 data/best_foot_forward.db \
  "SELECT file_type, file_path FROM file_registry WHERE jd_id IS NULL;"
```

## Logseq graph (pipeline pages)

The company/application/prep/notes layer is mirrored to a Logseq graph at
`data/BestFootForward/` (`pages/`, `assets/`, `journals/`, `logseq/`), registered
as the `bff` graph in `markdown-graph-mcp`. Markdown is master for the pipeline;
SQLite is the library master + a rebuildable index. See
[ADR-0008](adr/0008-logseq-graph-pipeline-master.md).

```bash
# DB -> pages (whole graph, or one company)
python3 -m best_foot_forward.utils.export_graph
python3 -m best_foot_forward.utils.export_graph --only 'Acme'

# hand-edited pages -> DB index (run before DB-backed reports if pages were edited)
python3 -m best_foot_forward.utils.reconcile_graph --dry-run
python3 -m best_foot_forward.utils.reconcile_graph

# regenerate the Home + Leads dashboards (+ optional cross-graph pulse)
python3 -m best_foot_forward.utils.generate_home
```

- Pages: `{Company}` entity + `{Company}/{Role}/Application|Prep|Notes` + `{Company}/Notes`.
- Config: `logseq/config.edn` sets `:file/name-format :triple-lowbar` (so `/` in a
  title maps to `___` on disk) and `:journal/page-title-format "yyyy/MM/dd"` (dates
  become a Year/Month/Day namespace index). `generate_home.py` additionally ensures
  Home, Leads Dashboard, and Applications Dashboard are favorited (`:favorites`) —
  Logseq's default landing page is Journals, with no visible link to any of these
  otherwise. Additive only: a page favorited by hand in the Logseq UI is never
  removed or reordered.
- **Never** `rm pages/*.md` before an export — it deletes hand-authored pages.

## Transcripts and recordings workflow

- Raw audio from `live_transcribe.py` is saved to `data/media/recordings/`.
- Transcribe and route to an application directory: `python3 src/best_foot_forward/utils/transcribe.py <file.wav> --company "Kuat Design Systems" --role "Senior Software Engineer"`. Writes to `data/applications/Kuat_Design_Systems/Senior_Software_Engineer/`.
- Transcripts not yet attributed to an application go to `data/media/transcripts/` (the default).
- Raw audio files are preserved — do not delete them. Future STAR corpus analysis may use them directly.

## Utility modules

Everything under `src/best_foot_forward/utils/`. You rarely call these by hand — the
slash-command workflows in [commands.md](commands.md) invoke them — but knowing which
module owns which step is what makes a failure legible.

### Document generators

Each reads a session scratch file from `data/session/` and writes a document. The
workflow writes the scratch file; the generator turns it into an artifact.

| Module | Reads | Writes | Workflow |
|---|---|---|---|
| `generate_resume.py` | `resume_data.py` | tailored resume `.docx` + `.txt` | `/resume-tailor` |
| `generate_letter.py` | `letter_data.py` | cover letter `.docx` + `.txt` | `/resume-tailor` |
| `generate_prep.py` | `prep_data.py` | screening prep `.docx` | `/screening-prep` |
| `generate_interview_prep.py` | `prep_data.py` | interview prep `.docx` | `/interview-prep` |
| `generate_star_prep.py` | `star_data.py` | STAR flash-card `.docx` | `/star-prep` |
| `generate_thankyou.py` | `thankyou_data.py` | thank-you email `.txt` | `/write-thank-you` |

Session scratch files are overwritten every run and are not source of truth for
anything — see [ADR-0003](adr/0003-session-scratch-files.md).

> **Note:** the generators import their session module at import time, so they can only
> be run after the workflow has written one. `data/session/` is gitignored, so a fresh
> clone has none until the first tailoring or prep run.

### Pipeline and bookkeeping

| Module | What it does |
|---|---|
| `track_application.py` | Inserts the `applications` row after documents are generated — files written = applied. Creates the `jds` row if missing. |
| `track_bullets.py` | Records which canonical bullets and skills a given application used, including any text overrides. Called by `generate_resume.py`. |
| `auto_ghost.py` | Ages out stale applications to `ghosted` on CLI start and exit, using the same criteria as the ghost-candidates report. |
| `audit_log.py` | Append-only JSONL trail for automatic and unattended actions, so a hook that fired overnight is explainable afterwards. |
| `log_action.py` | Thin CLI wrapper over `audit_log.log_event`, for workflows driven from command markdown. |
| `import_secondary.py` | Shared lead-ingest used by the `sync_leads` MCP tool and `/push-leads`. Dedupes on `(company, role)` and UPSERTs, so a re-scored lead updates rather than duplicating. |

### Setup and one-time migrations

| Module | What it does |
|---|---|
| `init_graph.py` | Creates the Logseq graph and populates it from SQLite. Runs at the end of `/onboard`. |
| `init_document_prefs.py` | Seeds the `document_prefs` row (accent color, font) that the `.docx` generators read. |
| `relocate_assets.py` | One-time: moved the artifact tree into the graph's `assets/` and repointed the DB. |
| `migrate_jd_txt_to_md.py` | One-time: converted JD `.txt` files to `.md` with a Logseq property block. |
| `migrate_tailored_txt.py` | One-time: moved tailored `.txt` output into the per-role asset directory. |

The three migrations are kept for installs that predate those changes. A fresh clone
never needs them.

## Environment variables

None of these are required for normal single-machine use — `uv sync` + `/onboard` needs
none of them. They exist for multi-machine sharing, optional integrations, and
development/testing.

### Normal use, optional

| Variable | Default | Purpose |
|---|---|---|
| `BFF_ROLE` | `standard` | `standard` (standalone, no sharing) / `primary` (receives leads, does tailoring) / `secondary` (generates leads, exports to primary over MCP). See [docs/README.md](README.md)'s machine-setup section and `src/best_foot_forward/utils/config.py`. |
| `BFF_SEVO_GLANCE` | unset (off) | Name of a page in a separate personal Logseq graph (Sèvo) that `generate_home.py` should also stamp a cross-graph "Job Search Pulse" summary into. A personal cross-project integration, not something a new install needs. |

### Development and testing only

Set by the tooling itself, not something you export by hand in normal use — documented
here so a stack trace or a script's own `--help` makes sense.

| Variable | Set by | Purpose |
|---|---|---|
| `BFF_DATA_DIR` | `tests/uat/run_uat.sh`, `tests/uat/compare_eval_models.sh`, a manual UAT invocation, or `/web` | Redirects `db.py`'s `DATA_DIR` (and everything derived from it — `ASSET_BASE`, the JD asset tree, session files) to a throwaway directory instead of the real `data/`. `resolve_jd_path()` and every script that resolves `DATA_DIR` honor it; anything reading a hardcoded `data/…` path instead is a bug (see `tests/test_db_query.py::TestBffDataDirIsolation`, `tests/test_generate_home.py` for two real incidents this class of bug caused). `web/mystery/setup.mjs` and the `bff-graph` plugin also honor it as of 2026-08-16 — `BFF_DATA_DIR=/path/to/demo ./web/mystery/start.sh [port]` points the whole web UI (DB browsing and the graph explainer) at a demo/UAT dataset instead of the real one, e.g. for screenshots. |
| `BFF_UAT` | same as above | Marks the session as a scripted/roleplayed test run, not a real user. `CLAUDE.md`'s "Execution context awareness" section governs what this changes — notably, the session-startup greeting is skipped entirely rather than reading `memory/project_status.md`, which lives in Claude Code's own project-memory (keyed by working directory) and is **not** reachable through `BFF_DATA_DIR` (found 2026-08-16 — see `tests/uat/CHECKLIST.md` §0). |
| `BFF_CHAT_HEADLESS` | `web/mystery/plugins/bff-chat/index.js` | Marks a session as a non-interactive `claude -p` subprocess spawned by the `/web` chat plugin, with no human present to approve tool permissions. See `CLAUDE.md`'s "Execution context awareness" section. |
| `BFF_EVAL_MODEL` | `tests/uat/compare_eval_models.sh` | Overrides the model `.claude/commands/evaluate-job.md`'s delegated scoring subagent uses (default: Sonnet), so the Haiku-vs-Sonnet comparison can be re-run without editing the command file. Irrelevant to real users — the default is the shipped, tested choice. |
| `BFF_CHAT_CLAUDE_BIN` | unset (defaults to `claude` on `PATH`) | Override for which `claude` binary `bff-chat`'s headless subprocess invokes — a dev/test hook, not a deployment setting. |
| `BFF_UAT_CLAUDE_BIN` | unset (defaults to `claude` on `PATH`) | Same idea for `tests/uat/*.sh` — lets a test stub a fake `claude` binary to dry-run the harness's own logic without spending real API cost. |
